# V0.7 — Multi-Context Analysis

## Overview

WDAIDT V0.7 introduces **Configurable Multi-Context Analysis**, allowing Gemini to analyze the latest user-AI interaction alongside relevant preceding exchanges from the same ChatGPT conversation.

In multi-turn conversations, responses often take their specific form because of prior instructions, constraints, clarifications, or corrections that occurred earlier in the thread. V0.7 equips WDAIDT to detect issues such as:
- Previously stated instructions or constraints that the AI overlooked or contradicted.
- Ambiguous follow-ups whose meaning depends on earlier messages.
- Repetitive explanations that ignore prior user clarifications.
- Evolving user objectives across the conversation.
- Opportunities to craft more effective follow-up prompts grounded in dialogue history.

---

## 1. Configurable Context Window

Users can configure the maximum number of previous exchanges included in the analysis via the side panel settings drawer:

- **0 previous exchanges** (Current exchange only — exact V0.6 single-turn behavior)
- **3 previous exchanges**
- **5 previous exchanges** (Default)
- **10 previous exchanges**

### Key Characteristics
- **Persistence**: Persisted across extension restarts in `chrome.storage.local` under key `wdaidt_context_window`.
- **Sensible Fallback**: If the stored value is missing, undefined, or invalid, the system safely falls back to the default of 5 previous exchanges without throwing errors.
- **Independence**: Operates independently of Response Style, Custom Instructions, and Analysis Depth settings.
- **Workflow Agnostic**: Applies identically to both manual **Why?** clicks and **Auto Analyze** stream-completion triggers.
- **Safe ID Generation**: Request ID generation, propagation, and stale-result protection remain completely independent of context capture.

---

## 2. Critical Rule: Context Limit Is a Maximum, Not a Minimum

The selected context window represents the **maximum** number of previous exchanges to include. It is never a minimum requirement.

| Selected Window | Available Previous Exchanges | Preceding Exchanges Included | Current Exchange Included | Analysis Status |
|:---:|:---:|:---:|:---:|:---:|
| 5 | 0 | 0 | Yes | Proceed (Single-turn mode) |
| 5 | 1 | 1 | Yes | Proceed |
| 5 | 2 | 2 | Yes | Proceed |
| 5 | 5 | 5 | Yes | Proceed |
| 5 | 12 | 5 most recent | Yes | Proceed |
| 0 | 8 | 0 | Yes | Proceed |

### Guaranteed Behaviors:
- WDAIDT never throws an error because fewer exchanges exist than the selected limit.
- WDAIDT never waits for additional conversation turns to appear before analyzing.
- WDAIDT never generates synthetic, placeholder, or duplicated turns to fill the window.
- The current prompt and response are always analyzed separately and never duplicated inside the historical context.
- If history capture fails or the thread is empty, the system gracefully degrades to current-exchange analysis.

---

## 3. History Capture & Turn Pairing Rules

Historical exchanges are extracted on demand directly from the active ChatGPT conversation DOM:

1. **Active Turn Identification**:
   - Leaf-level user turns and assistant response containers are discovered across light DOM and open shadow roots using the established multi-strategy pipeline (`role-attributes`, `message-id`, `conversation-turns`, `articles`, `modern-turns`, `content-blocks`).
2. **Turn Pairing**:
   - Nodes are partitioned into chronological turns.
   - For each user prompt, all assistant messages occurring prior to the subsequent user turn are evaluated.
   - When multiple assistant responses are present (e.g. regenerated responses or model revisions), the final/latest assistant response is paired with that user prompt.
3. **Current vs. Historical Separation**:
   - The final completed exchange is identified as the current interaction (`prompt` and `response`).
   - Preceding complete exchanges are returned in `history` in strict chronological order (oldest to newest).
   - If the latest user prompt has no assistant reply yet (pending or streaming), `paired: false` is reported and `captureLatest` surfaces `RESPONSE_PENDING` without submitting partial analyses.
4. **Conversation Isolation**:
   - Turns are captured exclusively from the active `<main>` scope of the focused ChatGPT tab.
   - No transcripts are persistently stored on disk or in extension storage; captures remain in-memory for the analysis operation only.

## 4. API Request Contract Extension

The `POST /analyze` endpoint accepts an optional `context` array containing preceding user-assistant exchanges in chronological order:

### Request: `POST /analyze`

```json
{
  "prompt": "Can you rewrite it using recursion instead?",
  "response": "Here is the recursive version: def fact(n): return 1 if n <= 1 else n * fact(n-1)",
  "context": [
    {
      "prompt": "Write a Python function to compute factorial.",
      "response": "Here is an iterative version: def fact(n): ..."
    }
  ],
  "request_id": "req-987-abc",
  "response_style": "Professional and direct",
  "custom_instructions": null,
  "analysis_depth": "Balanced"
}
```

### Schema & Fields:
- `prompt` (`str`, required, 1 - 8,000 chars): Current user message.
- `response` (`str`, required, 1 - 20,000 chars): Current assistant reply.
- `context` (`List[ContextExchange]`, optional, default `[]`): Ordered collection of preceding turns:
  - `prompt` (`str`, required, 1 - 8,000 chars): Earlier user message.
  - `response` (`str`, required, 1 - 20,000 chars): Earlier assistant response.
- `request_id` (`str`, optional): Client-generated tracking ID echoed back in response.
- `response_style` (`str`, optional): Tone preset.
- `custom_instructions` (`str`, optional, max 1,000 chars): Custom style guidance.
- `analysis_depth` (`str`, optional): `"Brief"`, `"Balanced"`, or `"Detailed"`.

### Compatibility:
- Callers sending requests without `context` or with `context: []` or `context: null` remain 100% supported.
- The V0.6 dynamic analysis document response format (`AnalysisResult` and `AnalysisDocument`) is preserved without changes.

## 5. Context-Size Management & Budget Enforcement

To guarantee deterministic, safe request sizes and prevent latency spikes, input size budgets are enforced both on the client and backend:

1. **Current Exchange Priority**:
   - Current user prompt: max 8,000 chars (`MAX_PROMPT_CHARS`).
   - Current assistant response: max 20,000 chars (`MAX_RESPONSE_CHARS`).
   - The current exchange is never truncated or dropped to accommodate history.
2. **Context Budget**:
   - Extension budget: `MAX_CONTEXT_TOTAL_CHARS = 30000` total characters for historical exchanges.
   - Backend acceptance limit: `MAX_CONTEXT_TOTAL_CHARS = 40000` chars and `MAX_CONTEXT_EXCHANGES = 20` exchanges.
3. **Filtering Algorithm**:
   - Candidate history is trimmed to the configured context window (e.g. 5 most recent complete exchanges).
   - If total character count exceeds the budget, the system prioritizes the most recent complete exchanges and drops older complete exchanges first.
   - Partial exchanges are never created or transmitted.
   - Strict chronological ordering (oldest to newest) is maintained across the filtered set.
   - Requests exceeding limits at the API boundary return standard HTTP 413 `PAYLOAD_TOO_LARGE`.

---

## 6. Gemini Master Prompt Integration

WDAIDT retains a single authoritative master analysis prompt (`ANALYSIS_SYSTEM_PROMPT`) extended with explicit multi-context operational guidelines:

1. **Primary Object of Analysis**: The latest user prompt and assistant response remain the primary focus.
2. **Context As Diagnostic Evidence**: Earlier exchanges are consulted solely to detect overlooked instructions, contradicted constraints, or ignored clarifications.
3. **Anti-Summarization**: Gemini is explicitly prohibited from summarizing or narrating the conversation transcript.
4. **No Manufactured Criticism**: If the latest response appropriately satisfies the request in light of context, the model reports that concisely without inventing problems.
5. **Prompt Injection & Untrusted Data Protection**: All conversation content (current and historical) is demarcated inside `<CONVERSATION_HISTORY>` and `<CURRENT_INTERACTION>` tags and treated strictly as passive data.

---

## 7. Captured Interaction UI Transparency

In the Obsidian-styled side panel, the **Captured Interaction** accordion header includes a compact indicator displaying the exact number of preceding exchanges included in the request:

- When 0 exchanges are included: `"Current exchange only"`
- When 1 exchange is included: `"Context: 1 previous exchange"`
- When N exchanges are included: `"Context: N previous exchanges"`

The displayed count reflects the actual exchanges transmitted to the backend after context window limits and size-budget enforcement.
